Docusign IAM · Building Agents 201

Risk-based routing: Docusign Agreement Desk + Agent Studio + Workflow Builder

Sales · NDA scenario

This lab follows the Sales / NDA motion. Fontara's Sales team handles NDA requests for new deals, partnerships, and prospect conversations — some arrive as a counterparty's draft to review, others start as a plain ask: "We need an NDA in place before this call." Both paths run through the same architecture.

Before you begin

Start here

0.1 · The scenario

At Fontara, Procurement and Legal onboard high-value vendors one email thread at a time.

A business user emails a draft vendor contract, Legal manually hunts for the liability cap and governing law, then someone routes it for signature. It is slow, inconsistent, and hard to audit. 

In this lab you replace that with an automated process: an Agreement Desk request starts a workflow that hands the contract to a Risk Analyst agent, which extracts the key terms and classifies risk. LOW risk goes straight to the vendor for signature; MEDIUM or HIGH risk waits for Legal.

At Fontara, Sales handles dozens of NDA requests per quarter — and every one goes through Legal manually.

Sometimes a rep receives a counterparty's draft NDA. More often, they simply need an NDA in place before a call: "Can we get an NDA signed with Brightpath before Thursday?" — no draft attached, no document to review, just a deal waiting to move. Legal processes both types the same slow way.

In this lab you replace that with an automated process using the NDA Gatekeeper pattern. A Sales rep submits an NDA request in Agreement Desk. A Maestro workflow calls the NDA Gatekeeper agent, which first searches Agreement Manager for an existing active NDA with that counterparty. If one already exists, the request closes immediately — no duplicate paperwork. If nothing is found, the agent collects three business inputs and drafts or sends Fontara's standard NDA template directly. Legal only sees the request if the deal warrants it.

Two paths, one agent. The NDA Gatekeeper is built for both use cases: (1) conversational — a rep invokes it via Ask Iris to check for an existing NDA and get a draft on the spot; (2) automated — Maestro calls it as a workflow step and routes the result deterministically. Same agent, same instructions, two surfaces. This lab builds the agent and wires path (2) through Maestro. Scenario 1 in Stage 3 exercises the "NDA already exists" path; Scenario 2 exercises the "no NDA, draft and send" path.

0.2 · The architecture

Four surfaces, one loop

Docusign LayerRole in this lab
Agreement DeskIntake and status hub. The Sales rep submits an NDA request here — no document upload required. Captures counterparty name, deal context, and deal value.
Agreement ManagerThe agreement repository. The NDA Gatekeeper agent searches here first, looking for an existing active NDA with the named counterparty before taking any action.
Workflow Builder (Maestro)The orchestrator. Triggers from the Desk request, calls the NDA Gatekeeper agent, and branches deterministically on what the agent found and did.
Agent StudioThe NDA Gatekeeper. Checks Agreement Manager, then either surfaces the existing NDA (and stops) or collects three business inputs and drafts / sends the standard NDA template. Works both as an Ask Iris conversational agent and as a Maestro workflow step.
eSignatureThe commit step. Nothing reaches a signer unless a branch explicitly routes to it.

Create request → Desk request event → Workflow Builder → NDA Gatekeeper agent (search Agreement Manager) → branch: NDA exists → close request / No NDA → draft + send template / High-value deal → Legal review first → send on approval.

Where this sits in the bigger picture: Agreement Manager is the repository that gives the agent its context — it knows what NDAs already exist, with whom, and whether they're active. Without Agreement Manager, the agent has no memory. Agent Studio is the control plane where you design and govern the agent. Maestro is the deterministic orchestrator that calls the agent and acts on the result. The NDA Gatekeeper pattern demonstrates how all three work together.
This lab builds the agent for the Maestro workflow path. The same agent works conversationally in Ask Iris — a rep can type "Do we have an NDA with Brightpath?" and get an answer instantly without submitting a request. That conversational path is demonstrated in Stage 1.4. The Maestro-wired path is what Stages 2 and 3 build and test.

0.6.5 · Define your contracting standards

setup

The agent classifies risk against a policy. Without defined thresholds, every classification is a guess. Before the lab — or before deploying to production — document your NDA playbook. At minimum, answer these questions:

ThresholdExample valueWhere it lives
Acceptable governing lawCalifornia, New York, Delaware; anything else = MEDIUM or HIGHAgent Instructions or Knowledge Source
Maximum NDA term without escalation3 years standard; 5 years = MEDIUM; perpetual = HIGHAgent Instructions or Knowledge Source
NDA type policyMutual preferred; one-way (Fontara-bound only) = MEDIUM; one-way with no reciprocal = HIGHAgent Instructions
Exclusion carve-outsStandard exceptions (public domain, prior knowledge) = LOW; unusual carve-outs = MEDIUM or HIGHAgent Instructions

Two ways to encode your playbook:

  • Inline in Instructions — paste the thresholds directly into the agent's Instructions field (as in Stage 1.2). Simple, readable, good for labs and early production. Change the thresholds by editing the agent and republishing.
  • Knowledge Sources — upload a PDF or document containing your NDA playbook to the agent's Knowledge Sources. The agent queries it at runtime. Better for production: Legal can update the playbook document without touching the agent's Instructions, and the source is versioned and auditable separately.
For this lab, the thresholds are embedded in the Instructions prompt in Stage 1.2. For a production deployment, move them to a Knowledge Source so Legal owns the policy without editing the agent.

0.8 · Best practices & gotchas

These are the issues that reliably burn time in workshops and early production deployments. Read them before you build.

Keep your test documents short

The agent step has request-size and execution timeout limits. A 1–3 page NDA processes in seconds; a 40-page MSA may time out or return a degraded response. Use short, clean sample documents in workshops. In production, if you need to handle large documents, test your specific document size against the limits before going live and build the fallback branch to catch timeouts.

The agent must be Published — not Draft — before you import the workflow

A Draft agent does not appear in Workflow Builder's agent picker. Publish the agent in Stage 1 before opening the workflow import in Stage 2. If the dropdown is empty, go back and publish first. This is the single most common reason Stage 2.5 gets stuck.

The workflow must be Published — not Draft — before you submit a request

Agreement Desk can only trigger a published workflow. "Nothing happens when I submit" almost always means the workflow is still a draft. Publish it before testing in Stage 3.

JSON case sensitivity: "exists" not "Exists"

The branch step compares nda_status as a literal string. "exists" matches; "Exists" or "EXISTS" fall through to the fallback path. Your agent Instructions must specify the exact lowercase values — exists, drafted, sent, error — and you must verify the JSON output in the Test panel before moving on (Stage 1.4).

One document per request — no more

The Get Document from a Request step retrieves one document. If a request has multiple attachments and no document labels are configured, which one it returns is undefined. Keep it to one document per request in this lab. In production, configure document labels on the Request Type and point the step at the correct label.

Re-point tenant references after every import

Imported workflows and Request Types carry references from the source tenant: Request Types, agents, statuses, connected systems, and recipients. None of these survive import cleanly. Work through Stage 2.3–2.6 in order — do not skip ahead to Stage 3 before every step is re-pointed and verified.

The one-time agent consent must happen before the first live run

The agent step runs as a named admin identity in your tenant. That admin user must complete a one-time consent in the Docusign environment before the step will execute. Do this before publishing the workflow. If the workflow publishes successfully but the agent step silently fails on the first run, the missing consent is almost always why.

1.2 · Replace the instructions with the Gatekeeper prompt

The initialization in 1.1 generates a starting prompt. Replace it entirely with the tested, curated prompt below. The four steps cover: thorough search, pivot if not found, interactive intake (no guessing), and NDA generation. The final block adds a structured JSON output requirement so the Maestro workflow can branch on the result.

Instructions — paste this in full, replacing any generated text
Role & Core Objective: You are an NDA Gatekeeper Assistant for Fontara's Sales team. Your job is to check the Docusign repository for existing agreements with a specified counterparty. If none exist, you guide the user through drafting a new standard NDA. You operate in two modes: conversational (invoked via Ask Iris) and automated (called as a Maestro workflow step). In both modes, the logic is identical. Step 1 — The Thorough Search (Preventing False Negatives): When given a company name, use the Find Agreements capability to search Agreement Manager. - Real-World Guardrail: Look for exact matches AND partial matches. If the user types "Brightpath", check for "Brightpath Technologies" or "Brightpath Inc." before declaring zero results. - If you find an active, non-expired NDA with that counterparty, show a quick summary list of what exists and stop. Do not offer to draft a new NDA. Step 2 — The Pivot (Handling the Unhappy Path): If your search returns ZERO results, or if the only agreements found are "Expired" or "Terminated", trigger this exact response, injecting the company name: "I searched our records and could not find an active agreement for '[Company Name]' in Docusign. To protect our company, we need to put an NDA in place before moving forward. Would you like me to draft one for you right now?" Step 3 — Interactive Intake (Do Not Guess): If the user confirms (conversational) or the inputs are already available from the Maestro workflow request form, collect or confirm these three details: 1. Official corporate legal name of the counterparty 2. State for governing law (e.g., "California") 3. Business purpose of the discussion (e.g., "Evaluating a software integration partnership") Sausage-Making Rule: Do NOT proceed to Step 4 until all three inputs are explicitly provided. If any are missing, ask for them specifically. Step 4 — NDA Generation: Once all three inputs are confirmed: - If called from Maestro: use the Generate Documents capability with the template named Fontara_NDA_Template, pre-filling the counterparty name, state, and business purpose. - If invoked conversationally and no template send is configured: output the complete NDA text inside a single Markdown code block so the user can copy the entire document cleanly with one click. Return a structured result in this exact JSON format: { "nda_status": "exists | drafted | sent | error", "counterparty": "string", "existing_nda_summary": "string — populated if nda_status is exists, empty otherwise", "action_taken": "string — brief description of what the agent did" } Constraints: - When called from a workflow, always return valid JSON. Return nothing before or after the JSON object. - Do not guess missing inputs. Ask. - Do not take actions beyond finding agreements, drafting NDAs, and sending the NDA template. - Be precise and neutral. This is internal process support, not legal advice.
Why the two-mode design: the same prompt works for both Ask Iris (conversational) and Maestro (automated) because the logic is identical in both paths — search first, pivot if not found, collect inputs, generate. The only difference is output format: Maestro needs the JSON block; chat output wraps the NDA text in a code block for clean copy-paste. The prompt handles both.

1.4 · Test conversationally, then publish

Test the agent via the Ask Iris conversational interface first — this is faster than a full workflow run and immediately shows you whether the search and pivot logic work correctly.

  1. Click Test to open the test panel.
  2. Type: Do we have an NDA with Brightpath Technologies? — this should trigger Step 1 (the search). Verify the agent searches Agreement Manager and reports what it finds.
  3. Try a counterparty you know has no agreement: Do we have an NDA with Axiom Global Partners? — this should trigger Step 2 (the pivot script). Verify the agent delivers the word-for-word pivot response.
  4. When the agent asks if you want to draft one, say yes. Provide the three intake inputs and verify the agent outputs a complete NDA text in a code block (Step 4).
  5. Check that the final response also includes the JSON block: nda_status, counterparty, existing_nda_summary, action_taken. This is what the Maestro workflow will read.
  6. Click Save draft, then Publish and confirm.
Checkpoint: a published NDA Gatekeeper Assistant that (a) finds existing NDAs in Agreement Manager, (b) pivots and collects inputs when nothing is found, (c) generates the NDA text, and (d) returns valid JSON — selectable from the Maestro workflow's agent step.
It must be Published, not Draft. A draft agent does not appear in the workflow's agent picker in Stage 2.2.
The conversational test in 1.4 doubles as a demo-ready experience. Once published, a Sales rep can invoke this agent through Ask Iris from Agreement Manager without ever submitting a formal request — useful for quick checks before a call. How the agent's output reaches the branch

The agent returns a JSON object with four fields. The workflow captures nda_status, counterparty, existing_nda_summary, and action_taken into workflow variables so the branch can read them. In the imported workflow this mapping is already wired; open it and confirm the four variables are populated from the agent's response, and that nothing shows as unmapped.

The agent handles the Agreement Manager search internally via the Find Agreements capability. You do not need a separate "Get Document" step for this pattern - the agent does the lookup as part of its Step 1 logic and surfaces the result in nda_status.

2.6 · Walk the branch & the three paths

Open the branch step. Confirm three cases, then follow each path so you know what to expect in Stage 3.

CaseConditionPath
1 · NDA existsnda_status == "exists"Set the Desk status to NDA Active and send the requester the existing agreement summary. No new NDA is drafted. Request is closed.
2 · NDA drafted or sentnda_status == "drafted" OR nda_status == "sent"For standard deals: the agent has already generated the NDA via Fontara_NDA_Template — the workflow sends it for signature using the envelope the agent produced. For high-value deals: route to a Legal review Approval step first; send only on approval.
3 · Fallbacknda_status == "error", empty, null, or unexpected value — plus failure paths from the agent step itselfSet a Returned status and send the requester a message asking them to resubmit. No envelope.

Two things to set for your own tenant as you walk through:

  • Send step recipients - for the lab, use yourself as the internal signer and another participant (or the counterparty name from the request fields) as the external signer.
  • Legal approver (path 2, high-value branch) - use a shared test account. The approval task will surface the agent's existing_nda_summary and action_taken so the approver sees exactly what the agent found and did.
Message the fallback path sends to the requester
We tried to process your NDA request automatically but encountered an error. Please check the counterparty name and resubmit. If the problem persists, contact Legal directly.
The fallback is a real case, not an afterthought. An unexpected nda_status value silently matching the "sent" condition would dispatch a blank NDA envelope. The design default is not sending unless nda_status is exactly right.

3.2 · Scenario 2 — No NDA, standard deal, auto-send template

3.4 · Validation checklist

  • Agent - returns valid JSON with all four fields (nda_status, counterparty, existing_nda_summary, action_taken); nda_status is always one of the four literal values (exists, drafted, sent, error); capabilities include Find Agreements and Generate Documents.
  • Agreement Manager search - the agent performs both exact and partial name matching; a partial input like "Brightpath" finds "Brightpath Technologies."
  • Agreement Desk - the Request Type imported and activated cleanly; statuses advance correctly for each branch (NDA Active, NDA Sent, Rejected, Returned).
  • Workflow - published, not draft; the trigger fires only for the NDA Lab Request Type; all three branches are reachable; the fallback handles error and unexpected values without sending an envelope.
  • eSignature - envelopes are dispatched only on the "drafted/sent" path (and only after Legal approval on high-value deals); completion updates the Desk request status.

3.5 · Limitations & guardrails

Availability

Agent Studio and agent-in-workflow steps are in Limited Availability at time of writing: North America, English UI, on IAM Professional / Enterprise / IAM for Sales / IAM Platform plans, non-FedRAMP environments. Confirm with your PSA which of your accounts are activated or release dates.

Agent step constraints

  • Request size, execution timeout, and rate limits all apply to the agent step. 
  • Use short sample documents and simple prompts in workshops and demos. 
  • Agent output is probabilistic. Validate the shape, and always have a fallback branch - which is exactly why Scenario 3 exists.

Import constraints

  • Imported workflows arrive as drafts and need tenant-specific references re-pointed - Request Types, statuses, agents, connected systems, recipients.
  • Agent and newer step types may not map cleanly on import; verify them step by step rather than assuming.
  • Always do a test pass after importing, before declaring anything ready. That's what Stage 3 is.

Design guardrails

  • Humans in the loop for consequential calls. LOW can be automated; MEDIUM and HIGH should not be. Give the reviewer the agent's reasoning so review is fast, not skipped.
  • The agent scores, the workflow decides. Keep routing logic deterministic and auditable in Workflow Builder rather than asking the agent to take actions.
  • Scope capabilities tightly. A review agent needs to read documents. It does not need to send envelopes.
  • Fail closed. When in doubt, return the request - never send for signature on an assumption.

The message

Agreement Desk captured the NDA request → Workflow Builder invoked the NDA Gatekeeper → the agent searched Agreement Manager for an existing agreement with the counterparty, pivoted cleanly when nothing was found, collected the required inputs, and drafted the standard NDA via the envelope template — returning structured JSON the workflow could branch on → NDA already exists: closed the request instantly with zero duplicate paperwork / No NDA, standard deal: sent the template straight to signature / No NDA, high-value deal: queued Legal for approval before anything was sent. One agent, two invocation modes (Ask Iris + Maestro), five surfaces, fully auditable.

Reuse the pattern

The Search-to-Draft shape carries directly to other scenarios: checking for existing vendor agreements before onboarding, verifying an MSA is in place before a renewal, or any "check first, create if absent" workflow. Swap the agent's search criteria and the draft template; the five-surface architecture doesn't change.

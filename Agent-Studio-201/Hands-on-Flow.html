Docusign IAM · Building Agents 201

Risk-based routing: Docusign Agreement Desk + Agent Studio + Workflow Builder

Pick your persona

We will implement one repeatable architecture, two business motions. Procurement onboards vendors; Sales renews and expands customers. The same agent handles both , the toggle changes the category you select, who reviews escalations, and the closing status.


Before you begin

Start here

0.1 · The scenario

At Fontara, Procurement and Legal onboard high-value vendors one email thread at a time.

A business user emails a draft vendor contract, Legal manually hunts for the liability cap and governing law, then someone routes it for signature. It is slow, inconsistent, and hard to audit. 

In this lab you replace that with an automated process: an Agreement Desk request starts a workflow that hands the contract to a Risk Analyst agent, which extracts the key terms and classifies risk. LOW risk goes straight to the vendor for signature; MEDIUM or HIGH risk waits for Legal.

At Fontara, Sales and Customer Success process high-value renewals by emailing Legal and Finance.

Reps email draft renewal orders for review, so pricing and clause policy get applied inconsistently, high-value deals stall, and nobody can see where a renewal is stuck. In this lab you replace that with an automated process: an Agreement Desk request starts a workflow that hands the order form to a Risk Analyst agent, which extracts discount, term, and governing law and classifies risk. LOW risk goes straight to the customer for signature; MEDIUM or HIGH risk waits for Finance and Legal.

0.2 · The architecture

Four surfaces, one loop

Docusign LayerRole in this lab
Agreement DeskIntake and status hub. The business user starts here, uploads the contract, and can always see where the request sits.
Workflow Builder (Maestro)The orchestrator. Starts from the Desk request, fetches the document, calls the agent, and owns all the deterministic branching.
Agent StudioThe governed intelligence layer. Your Risk Analyst agent is a role-based digital team member with natural-language instructions and scoped data access - it reasons, it does not decide the routing.
eSignatureThe commit step. Nothing reaches a signer unless a branch explicitly allows it.

Create request → upload contract → Desk request event → Workflow Builder → Get Document from a Request → Risk Analyst agent → branch on risk → Send Documents for Signature → update Desk status.

Where this sits in the bigger picture : Docusign IAM is the governed agreement layer for agentic architectures - Agreement Manager, Agreement Desk, Workflow Builder, and CLM are the surfaces where agents actually live inside customer workflows, pre-sign through post-sign. Agent Studio is the control plane where you design and govern those agents. 
This lab builds one concrete pattern so you can adapt the same shape elsewhere. Embedding agents into CLM workflows via the "Use AI Agent" step is its own pattern, covered in 301.

0.5 · Learning objectives

Objective 1
Use Agreement Desk as a structured intake surface
Import a Request Type, submit a request, and attach the document the rest of the flow depends on.
Objective 2
Build a Risk Analyst agent in Agent Studio
Write instructions that reliably return valid, machine-parsable JSON, scope its capabilities, and verify with Test before publishing.
Objective 3
Orchestrate the agent inside Workflow Builder
Start from Agreement Desk, fetch the document, call the agent, capture its structured output into variables, and branch deterministically.
Objective 4
Keep humans in the loop and fail safely
Escalate MEDIUM/HIGH to the right approver, and return the request to the submitter when the automation can't do its job - never guess.

Stage 1 · Agent Studio

Build the Risk Analyst · 15 min

Build the agent first. It's the only artifact in this lab you create from scratch, it's where the actual skill lives, and the workflow you import in Stage 2 needs to point at it - so it has to exist first.

One agent serves both motions: it works out from the parties and context whether it's looking at a vendor contract or a customer renewal.

1.1 · Create the agent & set identity

  1. Log in to your Docusign account and select Automation from the global header (top navigation).
  2. Select Agents from the navigation pane on the left.
  3. The Agent Studio opens and the Agents page is displayed. Confirm you can see the Featured agents row, My agents below it, and a Create New button top-right.
  4. Click Create New.
  5. Click Use classic editor.
  6. Set the core properties by clicking the pencil icon next to "My new agent," then click Save:
PropertyValue
NameVendor & Renewal Risk Analyst
RoleRisk analyst
Description Pre-sign contract review for vendor onboarding and customer renewals. Extracts key terms and classifies risk; does not negotiate or send.
Use this exact name. In Stage 2.2 you'll select this agent inside the imported workflow. Matching the name the workbook expects makes that step unambiguous - and makes it much easier for your facilitator to help when something doesn't line up.

1.2 · Write the instructions

Paste this into the Agent's Instructions field. There is no separate output-schema builder in Agent Studio - the response shape you want is described here, in plain language, so be explicit about field names and allowed values.

Instructions
You are a contract risk analyst. You receive one contract at a time. 1. Determine whether this is a vendor contract or a customer renewal, based on the parties and context. 2. Extract the following fields: - risk_level: one of LOW, MEDIUM, HIGH - liability_cap: short human-readable description of the limitation of liability - governing_law: the governing jurisdiction or venue - term: total term or renewal period (for example "1 year" or "3-year initial term with 1-year renewals") - discount: any commercial discount (for example "10% discount on list price"), or "none" 3. Classify risk_level using these rules: - HIGH if there is no liability cap, or the cap is clearly nominal relative to the deal. - HIGH if a discount exceeds 30%, or the term is shorter than 12 months. - MEDIUM if the commercial terms are acceptable but the governing law is non-standard, or if any key term is ambiguous. - LOW only if the liability cap, term, discount, and governing law all look standard and unremarkable. - If you cannot confidently determine a key term, do not guess - choose MEDIUM or HIGH and say why in the field value. 4. Return the result as a single valid JSON object in exactly this shape: { "risk_level": "LOW | MEDIUM | HIGH", "liability_cap": "string", "governing_law": "string", "term": "string", "discount": "string" } Constraints - Always return valid JSON. Return nothing before or after the JSON object. - All five fields must be present on every response. Use "none" or "not specified" rather than omitting a field. - Be precise and neutral. This is internal policy evaluation, not legal advice. - Do not take external actions. Only analyze and return JSON.
Why the strictness matters: the imported workflow branches on risk_level as a literal string. A response wrapped in prose, or one that returns "Low" instead of "LOW", will fall through the branch conditions into the fallback path. Say "always valid JSON" and "all fields present" explicitly - and then verify it in 1.4.

1.3 · Configure capabilities & knowledge

Agent Studio agents don't declare a typed-input schema the way a function does. Context reaches this agent as the document the workflow attaches to the step, plus anything in the step's Chat Message. What you configure here is what the agent is allowed to do and what it already knows.

SettingWhat to configure
CapabilitiesClick Add and enable Find Agreements so the agent can open the contract the workflow passes it. Leave send and signature capabilities off - this agent only analyzes. Click on add one capability.
Knowledge SourcesOptional for this lab. In production this is where your risk playbook lives, so thresholds can change without editing Instructions.

1.4 · Test until the JSON is clean, then publish

  1. Click Test and give the agent a short sample agreement - paste text, or attach one of your sample contracts if the test UI allows.
  2. If the response renders as formatted prose, open Output Display and set Test Mode to Raw so you see exactly what the workflow will receive.
  3. Verify all five keys are present: risk_level, liability_cap, governing_law, term, discount.
  4. Verify risk_level is exactly LOW, MEDIUM, or HIGH.
  5. Test with both sample contracts and confirm they land on different risk levels - that's what Stage 3 depends on.
  6. Click Save draft, then Publish and confirm.
Checkpoint: a published Vendor & Renewal Risk Analyst that reliably returns well-formed JSON, and is selectable from a workflow's agent step.
It must be Published, not Draft. A draft agent will not appear in the workflow's agent picker in Stage 2.2.
Spend your time here rather than rushing to Stage 2. Every minute spent making the agent's output boringly predictable saves ten minutes of debugging branch conditions that "randomly" don't fire.

Stage 2 · Import & wire up

Request Type + workflow · 10 min

Both the Request Type and the workflow are prebuilt and supplied as ZIPs, so the whole room starts from an identical, working configuration. Your job here is to import them, re-point the tenant-specific references at your objects, and publish. What matters is understanding what's inside - open each step as you verify it.

2.1 · Import & activate the Request Type

  1. Open the Agreement Desk / Requests experience.
  2. Open Settings for Agreement Desk.
  3. Go to Request Types.
  4. Click Import and select the risk_lab_request_type.zip you downloaded in Stage 0.
  5. Confirm a new Request Type appears - for example Agent Studio - Risk Lab (your facilitator confirms the exact label).
  6. Check its status. The import activates the intake form for you, so it should already be usable. If you open the intake form and see an Activate button, click it - an un-activated form stays a draft and won't be available in the final request.
Checkpoint: the Request Type is listed and active, with fields for vendor/customer name, requester, estimated annual spend, jurisdiction, and category.
Importing rather than hand-building keeps everyone on identical field names, which matters in the next step - the workflow's trigger and field mappings expect exactly those names.

2.2 · Import the workflow

  1. Navigate to Agreements → Maestro Workflows (your tenant may label this Workflow Builder under Automation).
  2. Click Import Workflow.
  3. Choose the import option and click Upload.
  4. Browse to risk_lab_workflow.zip, select it, and click Open. Leave the file zipped - don't extract it first.
  5. Confirm the workflow opens on the canvas with its steps laid out: trigger → Get Document → agent step → branch → three downstream paths.
Checkpoint: the imported workflow is on your canvas as a draft, showing a start method of From Agreement Desk and a visible three-way branch.
An imported workflow will not run untouched. References to tenant-specific objects - your Request Type, your published agent, the consent identity, recipients - arrive unmapped or pointing at the source tenant. Work through 2.3 to 2.6 in order before publishing.

2.3 · Verify the trigger & Request Type

  1. Open the workflow's start / trigger configuration.
  2. Confirm the start method is From Agreement Desk.
  3. Set the Request Type to the Agent Studio - Risk Lab type you imported in 2.1.
  4. If the trigger has conditions referencing a request status, confirm those status names resolve to real statuses in your tenant.
Checkpoint: the trigger names your own imported Request Type, not a placeholder or a missing reference.
Request Type and status references are the most common thing to need re-pointing after a workflow import. If you see an error like "Module metadata is undefined" or a missing-request-type error, this is almost always the cause.

2.4 · Understand "Get Document from a Request"

This is the first step after the trigger. It pulls the uploaded contract off the Desk request into a workflow variable that both the agent step and the send step consume. Open it and confirm:

SettingWhat it should say
RequestThe current Agreement Desk request - the default driven by the start method.
Document selectionThe default: latest version. Requests in this lab carry a single attachment, so no label filtering is needed.
Output variableA document variable named request_document.
Checkpoint: you can point at where request_document is produced, and trace it forward to the two steps that consume it.
Known constraint worth internalizing: this step returns one document. If a request has several attachments you configure document labels on the Request Type and point the step at a specific label - otherwise which document you get is not something to leave to chance. That's why Stage 3 asks for one document per request.

2.5 · Point the agent step at your agent

Open the agent step (labeled Use AI Agent, Agent, or similar depending on your environment). Agent references often don't survive an import cleanly, so this is the step most likely to need your attention.

FieldValue

Agent ⚠️Select your agent: the published Vendor & Renewal Risk Analyst from Stage 1. If the dropdown is empty, your agent is still in Draft - go back and publish it.

How the agent's output reaches the branch

The agent returns a structured response - JSON or XML - containing the five fields. The workflow captures those into variables of the same name (risk_level, liability_cap, governing_law, term, discount) so the branch can read them. In the imported workflow this mapping is already wired; open it and confirm the five variables are populated from the agent's response, and that nothing shows as unmapped.

A note on Update Variable From XML: that step is documented for ingesting XML files into workflow variables. It's a legitimate advanced option if you're deliberately working with XML documents, but it is not the standard or required way to read an agent's output. The default path is the agent returning JSON/XML and the step's own mapping capturing it. In CLM's "Use AI Agent" step the response surfaces as AgentFinalResponseRaw and AgentFinalResponseXml for downstream steps - that CLM pattern is covered in 301.

2.6 · Walk the branch & the three paths

Open the branch step. Confirm three cases, then follow each path so you know what to expect in Stage 3.

CaseConditionPath
1 · Low riskrisk_level == "LOW"Send Documents for Signature using request_document, then set the Desk status to Onboarded / SignedRenewal Signed.
2 · Medium or high riskrisk_level == "MEDIUM" OR risk_level == "HIGH"Approval step carrying the agent's extracted terms, then into the same send step on approval. Rejection ends in a terminal Rejected status.
3 · Fallbackrisk_level empty, null, or unexpected - plus the failure paths from Get Document and the agent stepSet a Returned status and send the requester a message. No envelope.

Two things to set for your own tenant as you walk through:

  • Send step recipients - for the lab, use yourself as the internal signer and another participant (or the contact from the Desk request fields) as the counterparty.
  • Approvers - a Legal approver; use a shared test account.a Finance approver and a Legal approver; use shared test accounts.
Message the fallback path sends to the requester
We tried to process your request automatically, but could not read the attached contract or generate a valid risk assessment. Please check the document and resubmit this request.
Note how the fallback is a real case, not an afterthought. If an unexpected value silently matched the LOW condition, you'd have built a system that mails contracts to counterparties when the AI has a bad day. The design default is not sending.

2.7 · Publish the workflow

  1. Click Review & Publish in the workflow editor.
  2. Click through Next, then Publish.
  3. If prompted, click Authorize My Account to complete publishing.
  4. Confirm the admin identity from 2.5 has completed the one-time agent consent for this environment.
Checkpoint: the workflow shows as Published, and its trigger points at your active Request Type.
Must be Published, not Draft. Agreement Desk can only trigger a published workflow. If it still shows Draft when you reach Stage 3, publish it first - this is the single most common reason "nothing happens" when a request is submitted.

Stage 3 · Trigger & validate

Three scenarios · 25 min

Back to Agreement Desk. Submit a request for each of the three scenarios and confirm the flow lands where it should. A flow that only ever gets tested on the happy path is a flow whose behavior you don't actually know.

Each run follows the same shape: create the request, submit it, then attach the contract on the Documents tab via Upload documents.

The document is not an intake form field. Agreement Desk's form builder handles data-entry fields - text, number, dropdown, date. The contract attaches to the request itself via Upload documents, and the workflow retrieves it with Get Document from a Request. Keep it to one document per request.

3.2 · Scenario 2 - MEDIUM/HIGH risk, human review

Create another request; Vendor name DataVault Dynamics, spend 1500000, Jurisdiction EMEA, Category Vendor Contract. Submit, then attach the HIGH sample via Upload documents.

Create another request; Customer name Keranos Digital Media, spend 1500000, Jurisdiction EMEA, Category Customer Renewal. Submit, then attach the HIGH sample via Upload documents.

Open the approval task and read it as the approver would. The point of this pattern is that the reviewer gets the agent's findings handed to them - they shouldn't have to re-read the contract to know why it escalated.

3.3 · Scenario 3 - missing or malformed document, fallback

Create a third request with any valid field values, then either attach nothing at all, or attach a deliberately unusable file - an empty document, or an image with no readable text.

Expect: Get Document or the agent step fails → the fallback branch runs → the Desk status becomes a Returned state → the requester receives the explanatory message → no envelope is sent.
Optional fourth run: repeat Scenario 2 but reject the approval instead of approving. Confirm it lands in a terminal Rejected status and no envelope is ever created.

3.4 · Validation checklist

  • Agent - returns valid JSON with all five fields; risk_level is always one of the three literal values; capabilities let it read the document but not send anything.
  • Agreement Desk - the Request Type imported and activated cleanly; requests carry one document; statuses advance at each stage and reviewers can see the AI-determined risk and reasoning.
  • Get Document - request_document is populated, and the same variable feeds both the agent step and the send step.
  • Workflow - published, not draft; the trigger fires only for the right Request Type; all three branches are reachable; failure paths route to fallback rather than falling through to signature.
  • eSignature - envelopes carry the correct document and recipients; completion updates the Desk request.

3.5 · Limitations & guardrails

Availability

Agent Studio and agent-in-workflow steps are in Limited Availability at time of writing: North America, English UI, on IAM Professional / Enterprise / IAM for Sales / IAM Platform plans, non-FedRAMP environments. Confirm with your PSA which of your accounts are activated or release dates.

Agent step constraints

  • Request size, execution timeout, and rate limits all apply to the agent step. 
  • Use short sample documents and simple prompts in workshops and demos. 
  • Agent output is probabilistic. Validate the shape, and always have a fallback branch - which is exactly why Scenario 3 exists.

Import constraints

  • Imported workflows arrive as drafts and need tenant-specific references re-pointed - Request Types, statuses, agents, connected systems, recipients.
  • Agent and newer step types may not map cleanly on import; verify them step by step rather than assuming.
  • Always do a test pass after importing, before declaring anything ready. That's what Stage 3 is.

Design guardrails

  • Humans in the loop for consequential calls. LOW can be automated; MEDIUM and HIGH should not be. Give the reviewer the agent's reasoning so review is fast, not skipped.
  • The agent scores, the workflow decides. Keep routing logic deterministic and auditable in Workflow Builder rather than asking the agent to take actions.
  • Scope capabilities tightly. A review agent needs to read documents. It does not need to send envelopes.
  • Fail closed. When in doubt, return the request - never send for signature on an assumption.

The message

Agreement Desk captured the request and the document → Workflow Builder fetched it and orchestrated the run → an Agent Studio Risk Analyst read the contract and scored the risk → deterministic branching sent LOW straight to eSignature, MEDIUM/HIGH to a human, and anything broken back to the submitter. Intake once, analyze with an agent, route with Workflow Builder, sign with eSignature: all inside Docusign, all auditable.

Reuse the pattern

The same four-surface shape carries directly to other scenarios: NDA triage, customer renewals, procurement inbound review, or any department-specific risk workflow. Swap the agent's instructions and the branch thresholds; the architecture doesn't change.

Hands-on Lab (WIP)

CLI login & upload → extraction in Agreement Manager → MCP via Copilot Studio → Agent Studio

The scenario

At Fontara, procurement is buried in vendor contracts and PDFs and you're here to change that.

Today, the procurement team owns thousands of vendor agreements, MSAs, SOWs, and NDAs, all stored as flat PDFs across shared drives and inboxes. The documents are signed and safe, but the agreement data the business cares about is locked inside.

That means nobody can answer the questions leaders actually ask: Which contracts auto‑renew next quarter? Which vendors are on payment terms longer than 45 days? Where are we missing a price‑increase cap? What is our total committed spend with this supplier? Today, every question means a human opening files one by one and reading them manually.

Over the next hour, you are going to change that with Docusign, AI, and MCP. You will treat agreements as data, not just documents, and you will do it the way developers fix things: automated, repeatable, and scalable — not by hand.

Your build, stage by stage
  1. Stage 1 · Model & ingest: define the procurement agreement types and fields as code, then bulk-ingest the legacy repository with the Agreement CLI.
  2. Stage 2 · Extract: watch Docusign's AI turn each PDF into structured fields (supplier, renewal date, payment terms, liability caps).
  3. Stage 3 · Ask: wire up the MCP server so Fontara's procurement team queries the whole corpus in plain English from Copilot Studio.
  4. Stage 4 · Ship: hand them a Procurement agent that lives in the tools they already use.

This is the pattern: export the legacy repo → standardize with IAM Toolkit → ingest via API → operationalize with agents.

Prerequisites, set up before the session Do this first

Get every developer's machine ready before Stage 1 so the 15-minute CLI slot is spent on the workflow, not on installs. Everything here uses the demo environment and synthetic data only, no production accounts or real vendor data.

0.1 · Tooling on each machine

  1. Node.js LTS + npm installed (the Agreement CLI is distributed on npm).
  2. Docusign Agreement CLI installed globally:
    npm i -g @docusign/agreement-cli
  3. Confirm the ds command is on the PATH, running it with no arguments prints the help / command list:
    ds

0.2 · Accounts & access

  • A Docusign developer / demo account with IAM Toolkit (open beta) access enabled.
  • Permissions to configure Agreement Manager (agreement types, fields, ingestion) in that account.
  • For Stage 3: a Microsoft 365 / Copilot Studio environment where you can add a Model Context Protocol tool.

0.3 · Sample material to have on hand

  • The provided sample procurement agreements (MSAs / SOWs / NDAs), split into a train and a test set for Stage 1.
  • The workshop kit (sample agreements + workflow) from the shared GitHub repo, for the Copilot Studio stage.
Ground rule: use synthetic / non-production data only.

Stage 1 · IAM Toolkit + Agreement CLI 15 min

This is where you start Fontara's build. You log in with the Docusign Agreement CLI, define Fontara's procurement agreement types & fields as code, then bulk-ingest their sample repository. The pattern to emphasize: export legacy repository → standardize via IAM Toolkit → ingest via API at scale.

Why IAM Toolkit, the developer value story. The IAM Toolkit lets implementation partners and enterprise developers configure, test, and deploy Docusign Agreement Manager, the searchable, AI-powered agreement repository, programmatically, accelerating time-to-value. Talking points to land in this stage:
  • Faster deployments, reduces implementation time by over 40% vs. manual configuration.
  • Higher extraction accuracy, define AI training datasets as code and validate them programmatically.
  • Multi-account portability, deploy validated configs dev → prod, or replicate across accounts.
  • Scalable, partner-led implementations, a repeatable, version-controlled asset developers hand to each client.
Refs: implement-at-scale · configure types & fields · test customizations · deploy · bulk-ingest

1.1 · Authenticate

Browser-based OAuth. Each developer logs in with their own Docusign developer account, no shared or production credentials. Use the production flag only when you deploy in 1.6.

ds auth login

Expect: a browser tab opens, you grant access, and the CLI confirms the authenticated account. (For production later: ds auth login -e production.)

1.2 · Scaffold the workspace & project

Create the version-controlled project structure the rest of the flow reads from, the repeatable asset developers hand to each client.

ds scaffold -w my-docusign-workspace -p my-project -f agreement-manager

Creates: {workspace}/{project}/agreement-manager/ with configs/, files/train/, files/test/, tests/, metadata/ and export/ folders.

1.3 · Configure agreement types & fields as code

Pull the current catalog, edit the manifest to model the procurement structure (MSA / SOW / NDA + fields), then push it back.

ds agm get catalog

Edit the manifest to add/adjust procurement agreement types and fields:

{workspace}/{project}/agreement-manager/configs/agreement-manager-manifest.json
ds agm upload

Snapshot the deployed catalog back into a manifest (useful to version or replicate across accounts):

ds agm catalog-to-manifest --all

1.4 · Test the customizations

Place sample agreements in files/train/ and files/test/, generate the test template, fill in expected values, then run, extraction is validated programmatically, as code.

ds agm test generate-test-template

Fill in expected field values in the generated tests file:

{workspace}/{project}/agreement-manager/tests/testing.csv
ds agm test run

Expect: a pass/fail comparison of extracted vs. expected values so you can tune types & fields before going wide.

1.5 · Bulk-ingest the agreement set

Ingest a whole directory of agreements at once, the "entire legacy repository, not one document at a time" moment.

ds agm ingest <directory path>

To attach metadata during ingest, first generate a metadata template, fill it in, then ingest with it:

ds agm ingest --directory <directory path> --generate-metadata-template
# fill in: {workspace}/{project}/agreement-manager/metadata/metadata.csv
ds agm ingest --directory <directory path> --with-metadata

1.6 · Deploy to production

The same validated config promotes dev → prod (or replicates across accounts), just re-auth against production and upload.

ds auth login -e production
ds agm upload
Developer takeaway: everything in 1.2–1.6 is config-as-code + CLI, so a client's entire repository can be standardized, tested, ingested, and promoted to production the same way, not one document at a time.

Stage 2 · Extraction surfaces in Agreement Manager

Now Fontara's PDFs stop being flat documents. Once the agreements are ingested, Docusign's AI extraction (Iris) reads each one and populates the fields you defined in Stage 1. This is where the "static PDF → structured data" moment lands for the room, and where procurement first sees answers instead of files.

2.1 · Open Agreement Manager and confirm the corpus

  1. Go to apps-d.docusign.com → Agreements → Completed.
  2. Confirm the uploaded MSAs / SOWs / NDAs appear with their agreement type applied.
  3. Open one MSA and show the auto-extracted fields side-by-side with the source PDF.

2.2 · Procurement fields to highlight on screen

Extracted fieldWhy procurement cares
auto_renew + term_endDrives the renewals dashboard, no more missed auto-renew windows.
payment_terms_daysSpot off-standard terms (e.g. > 45 days) across the vendor base.
notice_period_daysKnow exactly when a termination notice must go out.
total_contract_valueSpend visibility and vendor concentration.

2.3 · Custom extractions to add (procurement-specific)

  • Termination for convenience, presence + notice window.
  • Liability caps, capped amount / multiple of fees.
  • Price-increase caps, max % uplift per renewal.

Note: exact custom-extraction setup steps depend on the IAM Toolkit / Agreement Manager UI version, validate against the IAM Toolkit docs before the session.

Stage 3 · MCP via Microsoft Copilot Studio 30 min

Now the payoff for Fontara's procurement team: they stop hunting through files and just ask. You'll connect the Docusign MCP server to Copilot Studio and query Fontara's corpus in plain English, including agreements with vendors like SmartFactory Systems and FutureSkills Solutions from the sample set.

Prerequisites: a Microsoft 365 / Copilot Studio environment; a Docusign developer account; the demo environment at apps-d.docusign.com; and the workshop kit (sample agreements + workflow) from the GitHub repo. Use synthetic data only, no production accounts.

3.1 · Set up the Docusign sandbox

  1. Log into apps-d.docusign.com with your developer account.
  2. Upload the sample agreements to Agreement Manager (this is the corpus from Stage 1).
  3. Import the provided workflow into Workflow Builder and confirm it is Published (not draft).
  4. Validate that the referenced templates exist in the account.

3.2 · Create & configure the agent

  1. Sign in at copilotstudio.microsoft.com.
  2. Create a blank agent and name it "Procurement Agent".
  3. Enable generative orchestration: Settings → Generative AI → set to "Yes".
  4. Add an agent description, e.g.:
Agent description (procurement-adapted)Procurement agent that uses the Docusign MCP Demo connector to act on agreements, envelopes, templates, and workflows, for procurement teams managing vendor contracts, renewals, and obligations.
  1. Add system instructions: prefer Docusign MCP tools for live state, use Workflow Builder before eSign, and never fabricate agreement data.

3.3 · Add the Docusign MCP Demo connector

  1. Open the Tools tab → + Add a tool → Model Context Protocol.
  2. Search for and select "Docusign MCP Demo".
  3. Create a new connection: authenticate with your Docusign demo credentials and allow access.
  4. Add and configure the tool, then review the available tools (all enabled by default).
  5. Publish the agent.

3.4 · Verify the connection

Each prompt should trigger a tools/call in the activity map.

Verify P1List all my Docusign accounts.
Verify P2List all my agreements.
Verify P3List available Workflow Builder workflows.

3.5 · Scenario A, Vendor Agreement Insights

The questions Fontara's procurement team actually asks, now answerable in plain English across the whole vendor corpus.

A1 · Renewal exposureShow me all Fontara vendor agreements with auto-renewals in the next 90 days.
A2 · Vendor overviewFor SmartFactory Systems, which agreements are active today? List key terms: value, renewal date, payment terms, and notice period.
A3 · Off-standard termsWhich vendors sit on payment terms greater than 45 days, and which MSAs are missing a price-increase cap?
A4 · Vendor comparisonCompare SmartFactory Systems and FutureSkills Solutions side-by-side on obligations and clauses. Show me what SmartFactory Systems is missing that FutureSkills Solutions has in place.

Scenario A demonstrates: portfolio-wide renewal visibility · Agreement Manager extracting parties/dates/terms/clauses · vendor-to-vendor clause checks (payment terms / price protection) · compliant vs non-compliant contrast.

Stage 4 · Agent Studio, quick demo 10 min

You ship it. Fontara's procurement team gets a prebuilt Procurement agent running on the structured dataset you just built, answering questions and surfacing risk without anyone touching the underlying platform.

  1. Open the prebuilt Procurement agent in Agent Studio.
  2. Ask "What's in my vendor agreements?", it summarizes the vendor portfolio.
  3. Ask it to surface risks & obligations (uncapped liability, off-standard payment terms, imminent renewals).
  4. Connect back to MCP: the same agent can surface in third-party tools, Microsoft Teams and other AI clients, via the MCP server.
The one-line message: IAM Toolkit + CLI standardized and ingested the corpus → Iris AI extracted structured fields → MCP + Copilot Studio and Agent Studio turned that intelligence into answers, wherever the procurement team already works.
